# 章表架构：决策选项对比（2026-11-07）

> 背景：模板语料库（`docs/template-corpus.md`）结论是「核心 + 可选、别做固定大本」。
> 本文把「怎么落地」拆成 6 个决策，每个给 2–3 个选项、优劣、我的推荐、对现有代码的代价。
> **核心原则**：能不动章 key 就不动；能不迁移数据就不迁移。

---

## 现状（判断基线）

| 项 | 游戏 | 应用 |
|---|---|---|
| 章表 | `ceshuSchema` 23 编号章 + meta | `appSchema` 16 编号章 + meta，另有 4 章 AI 模型层（`ai_enabled` 开关） |
| 档位 | `meta.gdd_scope` = lite(9 章) / full(23 章) | 同字段，lite(6 章) / full(16 或 20) |
| 分派 | `visibleChaptersForDoc(doc)` 统一收口 | 同 |
| 规格层 | `documentSpec`（GAME_SPEC / APP_SPEC）已存在 | 同 |
| 编译期约束 | `CHAPTER_KEYS` 是联合类型，`Record<ChapterKey,X>` 遍布 196 消费者 | 应用章 key 是 string 空间，边界窄化 |

**关键事实**：章 key 一旦重排/改名，会牵动数据、导出、校验、AI 提示词、测试。**所以"可选"必须靠"可见性开关"，而不是"改章表定义"。**

---

## 决策 1：固定章表 vs 核心 + 可选

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 固定章表（现状） | 所有章永远显示 | 简单、零迁移 | 内容臃肿；用户不需要的章也要填 |
| **B 核心 + 可选（推荐）** | 章 key 定义不变；用 `meta.enabled_modules: string[]` 标记启用的可选模块；`visibleChaptersForDoc` 过滤 | 不迁移数据、可分档、可渐进 | 需定义"模块 → 章"映射；UI 要加开关 |
| C 用户自定义章表 | 运行时增删章 | 最灵活 | schema/字段/校验/导出全动态，工程复杂度爆炸；不建议 |

**推荐 B**。且**复用已有的 `ai_enabled` 模式**：把"AI 模型层"视为第一个可选模块，再逐步把游戏的市场/商业化/运营、应用的 ADR/术语表/里程碑做成模块。
**代价**：`visibleChaptersForDoc` 增加一层"模块过滤"；`meta` 加一个数组字段；无需改任何章 key。低风险。

---

## 决策 2：向后兼容（改名 / 合并 / 删除章）

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 只改标签，key 永不变（推荐）** | 章 key 不动，只改显示名/分组/顺序 | **零迁移**、零数据风险 | 历史 key 名可能与新语义不完全贴合（可接受，key 是内部标识） |
| B key 映射迁移 | `normalizeCeshu` 里加 old→new 映射表 | 语义更干净 | 一次性迁移逻辑要长期保留；导出/测试全要跟 |
| C 按模板版本解释 | 存 `template_version`，读时按版本走不同章表 | 最严谨 | 要维护多套章表与分支，成本高 |

**推荐 A**：这次"模板打磨"只调**显示名、分组、可选性**，**不动任何 key**。这样老文档打开完全一致，零迁移、零回归。
**代价**：无。唯一约束是"以后新增章才用新 key"。

---

## 决策 3：游戏与应用是否共用"核心 + 可选"机制

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 各写各的（现状） | 两套逻辑 | 简单 | 重复，容易漂移 |
| **B 共享机制、章表各自注册（推荐）** | `documentSpec` 已有注册表；把"模块开关"做成规格层能力（`optionalModules`），游戏/应用各自声明 | 一套机制、零重复；未来第三种文档只注册 | 要给 `DocumentSpec` 加字段 |
| C 合并成一套章表 | 游戏应用共用章名 | 无 | 章名语义冲突，已证明不可行 |

**推荐 B**。`DocumentSpec` 增加 `optionalModules: { key, label, chapters }[]`，`visibleChaptersForDoc` 统一按"档位 + 已启用模块"过滤。
**代价**：`types.ts` 加字段、`gameSpec/appSpec` 各补一份声明；`appSchema` 的 `ai_enabled` 迁到通用模块机制（可保留旧字段读取做兼容）。

---

## 决策 4：模板版本化

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 不版本化 | 老文档跟最新模板 | 简单 | 模板一改，老文档的章/标签可能"变样" |
| **B 记录版本 + 最小迁移（推荐）** | `meta.template_version`（如 `2026-11`）；缺省按当前解释；只对"破坏性变更"写迁移 | 可控、可追溯 | 要维护版本常量与迁移表 |
| C 完整多版本章表 | 每版一套章表 | 最严谨 | 成本过高，当前不需要 |

**推荐 B**：先只加字段与常量，**不写多套章表**；等真出现破坏性变更再启用迁移表。
**代价**：`meta` 加一个字符串；`normalizeCeshu` 补默认值。极低。

---

## 决策 5：文档编号（ID）

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 保持现状 | `ceshu_id`（8 位）+ 文件名 | 零改动 | 人读不友好 |
| B 引入 `SDD-0001` 业务编号 | 新增自增序号 | 像 RFC/PEP，便于引用 | 要维护序号状态、并发/迁移处理 |
| **C `ceshu_id` 为稳定 ID + 可选显示编号（推荐）** | 内部仍用 `ceshu_id`；UI/导出可显示 `SDD-xxxx`（由 id 派生或用户自定义） | 不引入状态机、可读性可加 | 编号不连续（但对内够用） |

**推荐 C**：**不新增自增序列**（避免并发/迁移坑）。如果确实要"像 RFC 一样连续编号"，再单独做。
**代价**：无（可选显示层）。

---

## 决策 6：可选章的默认行为

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 默认全参与 | 默认都显示 | 简单 | 又回到臃肿 |
| **B 默认不参与，手动开启（推荐）** | `enabled_modules` 缺省为空 | 轻、可控 | 用户要主动开 |
| C 按档位自动 | lite 只核心；full 核心 + 已启用 | 与"方向/细节"一致 | 需要和 B 组合 |

**推荐 B + C 组合**：
- `lite`（方向版）：只有核心章（+ AI 方向版补模型卡，沿用现有逻辑）。
- `full`（细节版）：核心章 + **用户已启用的可选模块**。
**代价**：`visibleChaptersForDoc` 一处逻辑；沿用 `ai_enabled` 已验证的模式。

---

## 推荐组合（一句话）

> **章 key 一律不动；用 `meta.enabled_modules` 做可选可见性；`documentSpec` 声明可选模块；`meta.template_version` 记录版本；不改文档编号；lite 只核心、full 核心+已启用模块。**

这套方案的迁移成本≈0（老文档 `enabled_modules` 缺省为空、`template_version` 缺省按当前），且完全复用 `ai_enabled` 的既有模式。

---

## 落地顺序与风险

1. **规格层加 `optionalModules`**（types + gameSpec/appSpec）——纯增量，无行为变化；
2. **`visibleChaptersForDoc` 接模块过滤**——用 `ai_enabled` 做第一个用例，保证等价；
3. **把 `ai_enabled` 迁到 `enabled_modules`**（保留旧字段读取兼容）；
4. **应用加开关 UI**（文档信息里勾选可选模块）；
5. **游戏再逐步把"市场/商业化/运营"设为可选**（游戏侧最后动，风险最高）；
6. **模板版本字段**最后加（纯记录，不影响行为）。

**风险点**：第 5 步动游戏章表的"可见性"，必须用现有 4136 测试兜底；建议每步单独提交、单独跑四道闸。
