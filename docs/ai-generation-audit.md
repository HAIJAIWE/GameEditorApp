## 二、执行编排：逐章串行，但跨章上下文实际缺失

代码事实（`AiFullGeneratePanel.tsx:106-165`、`ceshu.ts:93-134`、`ceshuAi.ts:191-317`）：

1. **逐章串行** for 循环，单章失败记录后继续，首章即失败则中断（合理：多半是本地模型服务没起）。
2. 每章调用 `aiGenerateChapter`，整篇生成用 `onlyEmpty: false`（整章全字段一次生成）。
3. `buildDraftPayload` 把**已生成的所有章节**作为 `draft` 传给下一章 —— 看起来有跨章上下文。
4. **但 `buildChapterPrompt` 实际只读**：`meta`（名称/类型/定位/平台）+ **当前章**字段与已有内容 + 用户输入 + 关键词约束。
   ⇒ `draft` 里其它章的内容**并没有进提示词**。

**判断**：好处是每章提示词大小稳定、不会上下文爆炸；代价是**后章不知道前章的设定**。跨章一致性只能靠生成后的事后检查（`validateCeshu` 的一致性项 + 成稿反审），而不是生成时约束。这是"看起来有记忆、实际没有"的隐性坑。

> **2026-11-07 已修**：`buildChapterPrompt` 新增「前文要点」——取**当前章之前**已写好的章节，压成带上限的摘要注入提示词
> （最多 6 章 / 每章 4 字段 / 每值 80 字 / 总长 1400 字；排除 meta；单字段定向生成不注入）。
> 只取前序章不读未来章，避免因果倒置。测试：`tests/unit/ceshuPriorDigest.test.ts`（7 例，含截断与边界）。

## 三、质量门与预算门：有，但都是"记录"不是"拦截"

| 机制 | 现状 | 问题 |
|---|---|---|
| 确定性评分门 | 每章生成后跑 `evaluateChapterDraft`（合并后重跑 `validateCeshu`，给出前后错误数/完成度变化） | 只写进 `quality` **返回值**，不阻断、不重试、不回写 |
| LLM judge | `runLlmJudge` 辅助维度，失败降级 `null` | 同上，仅记录 |
| 成稿反审 | `buildReviewPrompts` + 11 项对抗检查（`ADVERSARIAL_CHECK_PROBES`） | 建议性质，需人工触发 |
| 预算门 | `estimatedTokens` + `bulk` 确认（云端大范围先确认），`skipBudgetConfirm` 仅 `budget:null` 时跳过 | 是**确认门**，不是硬上限；`usageTotal` 只观测无熔断 |
| 重试 | ~~无自动重试~~ **已落地**：字段解析为空时追加严格 JSON 约束自动重试 1 次 | 服务不可用/取消不重试（不放大故障） |
| 空字段补齐 | 有 `onlyEmpty` 能力，但整篇生成只跑一遍 | 无"生成后自动补齐空字段"的二次循环（**未做**：会显著增加调用成本，属产品决策） |

**判断**：初版是"体检报告出来了，但不治病"——主结论 `QualityGateVerdict` 算完后前端只取走辅助的 `judge`。

> **2026-11-07 已修**：新增 `shouldRegenerateChapter`（只认净恶化：`errorDelta>0` 或 `completionDelta<0`，
> 刻意不用 `blocking`——那是整篇口径；也不用 `!improved`——"无变化"在整篇生成里是常态，会满屏误报）。
> 面板收集主结论 → 净恶化章显示徽标/汇总 → 一键重生成这些章。测试：`agentQualityGate.test.ts`（5 例）+ `aiFullVerdictPanel.test.tsx`（2 例）。
>
> **已修（重试）**：「调用成功但字段解析为空」（JSON 截断/格式坏）自动重试 1 次，追加严格 JSON 约束；
> 服务不可用/网络错/用户取消在 await 处抛错，直接进 catch 不重试。预算门已 `confirmed: true`，不重复弹确认。

## 四、三个硬结论

### 1. LLM 能生成"结构完整"的文档，但"内容完整"要看章
- **结构完整**：能。字段契约密（92.6% aiHint / 100% reviewHint），JSON 解析 + 字段清洗（`filterGeneratedFields` 丢弃未知键、空串）保证输出落在 schema 内。
- **内容完整**：不稳。三个缺口：
  - 应用档 aiHint 66% → 三分之一字段靠猜；
  - 跨章无上下文 → 前后设定易矛盾（虽有事后校验，但要人盯着）；
  - 无重试/无补齐循环 → 字段多的章一旦 JSON 截断，整章归零。
- **字段多的章风险最高**：`systems`/`tech` 这类章字段密集，整章一次生成最容易触顶。

### 2. 与市场对比：强在"契约与校验"，弱在"多轮与记忆"
- 主流 PRD 工具（Notion AI / ChatPRD / 墨刀 AI，2026 评测口径）强在**单份文档初稿**与**与协作工具集成**，普遍不提供"字段级契约 + 一致性校验门"。
- 本项目在**结构化字段契约、必填/人定分离、生成后校验**上明显更硬——这是差异化。
- 但主流 coding agent 的进化方向是**大上下文 + 多轮修正 + 自动验证**（Claude Code 1M token 上下文、SWE-bench Verified 80.8%）。本项目目前是"单轮逐章 + 事后校验"，正好缺这一环。

### 3. AI 能不能"彻底"根据文档完成项目：不能，但能做到"高质量初稿 + 可执行骨架"
- 客观数据：SWE-bench Verified 最高 **93.9%**，但它测的是"独立解决一个 GitHub issue"，**不是"从一份文档做完整个项目"**；交互式基准（Dialogue-SWEBench）解决率仅 **46.9%**，说明"该停下来问"本身仍是瓶颈。
- 2026 年 SDD（规范驱动开发）的共识是：**人定 spec → AI 按 spec 写 → 人审查 → 迭代**，而不是全自动。
- 本项目的定位恰好是 SDD 的**规格层**：规格 → 字段契约 → 校验门 → 交接包/项目文件夹 → 可玩原型。这条链是"给 AI 和人共同的施工图纸"，不是"按一下生成完整项目"。
- **能做的**：生成可执行的字段级规格、导出交接包、生成界面原型、按章节派工。
- **做不到的**：自动产出可上线代码、自动验收、自动修正跨章矛盾。缺的是"生成代码 + 自动测试 + 结果回灌"的闭环。
