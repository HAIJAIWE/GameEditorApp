# 策划书怎么写：中文（国内） vs 国际（西方）对照

> 承接 `how-studios-write-gdd.md`。这次中英两边都查了，做个对照。
> **诚实边界**：大厂内部文档仍不可见；以下中文来自网易游戏学堂（官方）+ CSDN 系统策划案指南，
> 国际来自 Wikipedia「Game design document」条目（中性）+ 行业通行讨论（标注为常识）。

## 一、中文（国内）怎么做

**核心单位不是「一份 GDD」，而是「按系统拆的系统策划案」**，且有非常固定的六区块骨架：

| 区块 | 回答什么 | 主要读者 |
|---|---|---|
| 系统概述 | 这个系统解决什么体验问题 | 所有人 |
| 功能清单 | 有哪些功能点、P0/P1/P2 优先级、依赖谁 | 程序、运营 |
| 规则与流程 | 玩家操作后发生什么（**状态机**：状态/事件/前置条件/目标状态/副作用；关键流程补伪代码） | 程序、测试 |
| 数值配置表 | 具体数字与公式（**字段名/含义/类型/取值范围/是否必填**） | 程序、数值 |
| 界面与交互 | 层级缩进列表 + 按钮状态表 + 动效触发点 | 美术、程序 |
| 异常与边界 | 空/满/重复/超时怎么办 | 测试、程序 |

配套习惯：
- **分工明确**：系统策划（怎么玩）／数值策划（寿命·节奏·平衡）／文案策划（代入感）。
- **活文档**：源文件用协作工具维护，**PDF 只是某版本的快照**；第二页放**变更记录表**（版本号/日期/修改人/修改内容/**影响范围**）。
- **术语表**放附录，统一「进度满/可领取」这类词。
- 口头禅是「**写得让下游少问几句**」——少写一句边界，测试就多提一个 bug。

> 为什么这么「规格化」：国内长期以 MMO / MOBA / 吃鸡 / 手游为主，商业化与数值驱动强，
> 文档必须「能直接进开发排期」，所以演化成接近**软件规格说明**的形态。

## 二、国际（西方）怎么做

Wikipedia 对 GDD 的定性很关键：

- **GDD = 「living software design document」（活文档）**，且 **「没有统一的行业标准格式」**（原文 *no set industry standard form*）。
- 生命周期：预制作阶段产出，可 pitch 前或后；之后**持续修订，有时每天更新**——从「基本概念纲要」长成「项目末期覆盖每个方面的详细清单」。
- 内容清单（覆盖部分或全部）：故事、变现、角色、关卡/环境、玩法、美术、音效音乐、UI/操作、无障碍、目标受众、开发时间表。部分主题会拆到**补充文档**。
- 载体：文字处理文档 **或在线协作工具**（wiki）。
- 发行商委托时，GDD 常作为**合同附件**。

（Wikipedia 条目**没有**覆盖「大 GDD 过时/没人读」的批评、「design pillars（设计支柱）」、「GDD 与 TDD 的区分」——这些是行业通行讨论，属**常识层**，非该来源；另见 `gdd-2026-state-of-practice.md` 里一页式/原型优先的讨论。）

## 三、对照表

| 维度 | 中文（国内） | 国际（西方） |
|---|---|---|
| 核心单位 | **按系统拆的系统策划案**（六区块固定） | **GDD / design doc**（整体+分系统，living doc） |
| 结构标准 | **高度模板化**（六区块几乎行业通用） | **明确「无统一标准」**，各家自定 |
| 分工 | 系统/数值/文案策划**强分工** | designer 更泛，常一人多职 |
| 数值 | **数值配置表**（字段/类型/范围/必填），Excel | spreadsheets，但更强调**原型/playtest 验证** |
| 文档形态 | 协作源文件 + **PDF 快照 + 变更记录表** | **living document**（每天更新）+ 在线工具 |
| 读者导向 | **显式面向程序/美术/测试/运营**四类 | 面向团队，但不那么显式按岗位拆 |
| 异常/边界 | **强制异常分支表**（空/满/重复/超时） | 有，但不如国内模板强调 |
| 设计 vs 执行 | **设计案（脑图）→ 执行案（文档）** 两阶段 | pitch → 逐步扩展，更松散 |
| 驱动 | **商业化 / 数值 / 付费**（F2P 手游） | 玩法 / 原型 / 体验验证（AAA + indie） |

## 四、共同点（比差异更重要）

1. **都是活文档**，不是一次定稿；
2. **都按系统/功能拆**，不是一篇散文；
3. **数值都进表**（Excel / 配置表），正文只写思路；
4. **都是沟通工具**，按读者取舍；
5. **都要求「可执行」**——写得让人能直接做。

**本质差异只有一句**：中文更**工业化/规格化**（六区块、状态机、字段表、异常表，因为要直接进排期）；
国际更**迭代/原型驱动**（承认无统一标准，靠 playtest 收敛）。但国际的 live-service/F2P 团队，其实也在向国内这种「数值+配置表+规格」靠。

## 五、对我们 24 章 schema 的定位

- 我们的**章节内容**（故事/变现/角色/关卡/玩法/美术/音频/UI/无障碍/目标用户/时间表）几乎 1:1 对应 **Wikipedia 的国际 GDD 内容清单** → 我们是**国际式内容广度**。
- 我们的**机读断言/数值账本/契约** → 更像**国内的数值配置表 + 断言** → 我们又带**国内式结构化/量化**。
- 结论：**我们是「国际内容广度 + 国内结构化严谨」的混合体**——这其实是个不错的定位，不偏科。

**三个可补的洞**（都不是大改）：
1. **读者维度**：国内强调「这段给程序还是美术」，我们 `reviewHint` 只做自检；
2. **原型/playtest 验证**：国际强调「文档之外靠原型收敛」，我们有机读断言但没有「原型验证」入口；
3. **设计案/执行案显式化**：对应「AI 起草→人审定稿」，`meta.status` 有字段却没绑流程。

## 六、开发人员每天真正看的是哪一份？（"通用那一份"）

**不是大 GDD，是一组固定工件。** 开发期天天打开的东西是：

| 角色 | 每天真正看的 |
|---|---|
| 程序 | **数据配置表**（字段/类型/范围）+ **功能规格**（状态机/接口/伪代码） |
| 美术 | **资源清单** + 界面层级 + 动效触发点 |
| 测试 | **用例/异常边界表**（空/满/重复/超时） |
| 数值 | **数值表**（产出/消耗/成长曲线） |
| 制作/主策 | 排期、优先级、影响范围 |

**共同脊柱 = 「系统规格 + 数据配置表」。** 中文叫「系统策划案 + 数值配置表」，国际叫「feature spec + data sheet」——
名字不同，**是同一件东西**。GDD 只是这堆东西的总称，没人开发时从头读它。

所以回答你的问题：
- **有「通用核心」，但没有「单一通用模板」**（Wikipedia 明确 *no set industry standard form*）；
- 若要一句话指出「开发人员看的那一份」——就是 **「系统规格 + 数据配置表」**，它是中英两边唯一的真交集；
- 原型（prototype）是它的**验证副本**：规格说不清的，跑一遍原型就定了。

### 对我们意味着什么

我们的**机读层**（`data_tables` / `ledger` / `numeric_assertions` / 字段契约）+ **机读包**（`ceshuBundle` 导出的 JSON）
其实就是「**开发人员/机器看的那一份**」——这恰好补上了真实工作流里最刚需、也最容易被"大 GDD"忽略的东西。
下一步可做的：把这个机读包再包装成一份**「开发规格」**（按角色切视图：程序看配置表与状态机、美术看资源、测试看边界），
让它真正成为「丢给程序就能开工」的交付物，而不是又一份要人从头读的文档。
