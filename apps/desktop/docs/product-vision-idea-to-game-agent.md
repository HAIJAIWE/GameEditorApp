# 产品方向：从「一句话想法」到「能玩的游戏」的智能体

> 定位澄清（2026-10-26）：这不是"策划书编辑器"，而是**面向普通用户的"想法 → 游戏"智能体**。
> 策划书 / 一页摘要 / 数据表 / 任务清单，都只是它的**中间产物**。下面基于**已有代码**谈，不画饼。

## 一、先把定位钉死

- **用户**：普通玩家/爱好者——有想法，但不会做游戏、也不懂 24 章 334 字段。
- **目标**：把"我想做个像 XX 的游戏 / 我有个点子"变成**能玩的东西**（可玩 demo / 可交付开发包）。
- **两种模式**：**复刻**（照着某个游戏做）或**创新**（原创点子）。
- **我们已有的优势**：schema + 阶段 + 模块 + 契约 + 机读数据 + 一页 + 岗位任务 + **文档→可玩 demo 生成器**。

## 二、三段流水线（对应已有能力）

```
① 需求采集（对话）        ② 设计生成（按模块展开）        ③ 实现生成
   一句话/一个参考游戏   →    立项一页 + 需要的系统模块   →    可玩 demo / 工程包
   （concept 7 章压一页）      （用 aiHint/reviewHint 契约）    （generateDemo 已有）
```

- **① 需求采集**：普通用户答不了 24 章。Agent 只问 3–5 个关键问题 + 给选项，产出**立项一页**（定位/核心循环/MVP）。
- **② 设计生成**：按用户勾选的**系统模块**展开（不是全 24 章），字段契约驱动 AI 起草。
- **③ 实现生成**：`ceshuDemoPrompt` + `scripts/generateDemo.ts` 已能把文档变成**单文件可玩 HTML**；再给程序则出**数据表 + 岗位任务清单**。

## 三、两种模式怎么走

**A. 复刻模式**（更好验证，建议先做）
```
用户："我想做个像《吸血鬼幸存者》那样的游戏"
  → Agent 拆解参考游戏：核心循环 / 系统 / 数值骨架
  → 生成"立项一页"（明确：复刻了什么、改了/砍了什么，避免抄袭）
  → 展开需要的模块 → 生成可玩 demo
```
要点：**明确标注"复刻点 / 改动点"**——既是差异化，也是合规。

**B. 创新模式**
```
用户："我有个点子：猫咪经营邮局…"
  → Agent 追问收敛：给谁玩？核心循环？单局多长？
  → 一页立项 → 模块展开 → demo
```

## 四、面向普通用户的三个硬规则

1. **别让他看到 24 章 / 334 字段**：schema 是 Agent 内部用的，用户只看「一页 + 下一步问题 + 能玩的 demo」。
2. **每步都有可见产出**：一页 → 原型 → 细化；快速反馈，别等全填完。
3. **机器可读的中间件**（我们已有 `ceshuBundle` 机读包）：让 Agent 能连续加工、也能交给别的 AI 继续做。

## 五、我们已有什么 / 还缺什么

| 能力 | 状态 |
|---|---|
| schema / 阶段 / 模块 / 契约 / 机读数据 | ✅ 已有 |
| 一页摘要 / 岗位任务 / 三种导出 | ✅ 已有 |
| 文档 → 可玩 demo（单文件 HTML） | ✅ 已有（`generateDemo`） |
| **对话式需求采集（intake agent）** | ❌ 缺 |

| **三段流水线的编排（idea→design→demo）** | ❌ 缺 |

## 六、最小可跑的第一步（建议）

**先做"复刻"单线**，因为**有参照物、最容易验证**：
1. 用户输入一个参考游戏名；
2. Agent 用固定模板拆出「核心循环 / 系统 / 数值骨架」；
3. 生成立项一页（标"复刻/改动"）；
4. 跑 `generateDemo` 出一个可玩 HTML；
5. 用户看到能玩的东西 → 再决定要不要深入。

这条线一旦跑通，"想法 → 游戏"就闭环了；创新模式只是把"参考游戏"换成"用户点子 + 追问"。

## 原型 ≠ 成品：三层交付（重要）

用户问："那个 HTML 应该算想法/原型吧？后续要完善，到时候就不是 HTML 开发了吧？"——**对，完全对。** 必须分清三层：

| 层 | 产物 | 目的 | 生命周期 |
|---|---|---|---|
| ① 想法层 | 立项一页（定位/核心循环/MVP） | 讲清"做什么" | 长期保留 |
| ② 原型层 | **可玩 HTML demo** | 验证"好不好玩、跑不跑通" | **一次性、可丢弃**，不是成品 |
| ③ 交付层 | **规格 + 数据表 + 岗位任务 + 机读包** | 给 Unity / Unreal / Godot 团队开工 | 长期维护 |
| （正式开发） | 引擎工程（Unity / Unreal / Godot） | 真正做游戏 | 项目主体 |

关键认知：
- **HTML demo 是"验证工具"，不是"成品"**。它唯一的价值是"让人 30 秒看到能不能玩"，跑完就可以扔；
- **真正"交给程序"的是层 ③**——而这层我们已经有了：`data_tables` / 机读包 / 岗位任务清单 / 数值断言；
- 所以产品不是"用 HTML 做游戏"，而是"**把想法变成：能验证的原型 + 能开工的规格**"。正式开发当然在引擎里，不在 HTML。

这也解释了为什么之前做的「岗位任务清单 / 数据表 / 机读包」很关键——它们才是**从"想法"通往"真开发"的桥**，HTML 只是桥上的一块试板。

## 补充：傻瓜入口，专业出口（2026-10-26）

用户定调：「这个项目就是做**数据 + 设计文档**，这是专业方向；生成后的产品可以**导出去给 AI 看**。」定位因此更清楚：

- **入口面向普通用户**（不懂 24 章 / 334 字段，AI 带着走）；
- **出口是专业级**：设计文档（一页 / 交付版）+ **数据**（数据表 / 断言 / 账本）+ **机读包**；
- **机读包可直接喂 AI**：`ceshuBundle` 导出的 JSON + `ceshuBundlePrompt` 消费提示词，就是"给 AI 看"的接口（**已实现**）。

一句话：**傻瓜入口，专业出口；人看的是一页/文档，AI 看的是机读包。**
这正是相对"直接在 AI 那边生成"的差异化——它们只给你一个 demo，你给的是**专业级文档 + 数据 + 可被 AI/程序继续加工的机读包**。

## 七、一句话

**你卖的不是文档，是"让不会做游戏的人，半小时看到一个能玩的自己游戏"。**
文档、一页、数据表、任务清单，都是这条路上的副产品——对内是引擎，对外只给"一页 + demo"。
