# 我们的策划书 vs 2026 年别人怎么写策划书：差在哪

> 澄清：**这个产品本身就是「策划书（设计文档）系统」**，不是"工具 vs 文档"两回事——下面比较的是
> 「**我们产出的这份策划书**」和「2026 年行业里别人怎么写/交付策划书」，不是拿工具去比文档。
> 前提照旧：2026 的「趋势」多来自模板/工具/学术（见 `gdd-2026-state-of-practice.md`），证据强度中等，别当铁律。

## 一句话结论

**方向高度一致，形态不同。** 2026 主流是「活的模板 / wiki」；我们产出的是「**一份策划书 + 一层 schema / 校验 / AI 引擎**」——
本质都是设计文档，只是我们这份更受约束、机器也认。
真正的差距只有三块（协作、读者导向、一页式交付物），而我们有两块反而**领先**（可执行校验、schema 驱动条件必填）。

## 一、对照表

| 2026 趋势 | 我们现在的实现 | 状态 |
|---|---|---|
| 活文档（living doc） | 版本链 + 变更日志 + 迁移；但**单机** | ◐ 半 |
| 一页 + 分层（MVP 优先） | 阶段分层（立项/研发/发行）+ **一页总览视图** | ● 对齐 |
| Markdown / 机读优先 | 机读层（JSON 机读包）+ 契约 + 断言 | ● 对齐 |
| AI 全程 + 量化 | aiHint/reviewHint 契约 + AI 起草 + 评分器 | ● 对齐 |
| 类型化模块（无万能章节表） | **通用底座 + 可选系统模块 + 模块勾选 UI** | ● 对齐 |
| 理论→机制映射 | numeric_assertions / design_claims（主张→证据核对） | ● 对齐 |

## 二、真正落后的三点

1. **协作活文档**：2026 的"活"=多人实时协作 wiki（IEEE VR 2026 的 Game Playbook、Nuclino 类）。
   我们是单机桌面 + 版本历史。这是**形态级差距**，不是补个按钮能解决的。
2. **读者导向**：国内系统策划案明确"这段给程序看、那段给美术看"；2026 也强调按角色取舍。
   我们的 `reviewHint` 是**审阅者自检**，没有"写给谁"这一维。
3. **一页式"交付物"**：我们有一页**视图**（看），但**导出**仍是逐章（给老板/程序的一页纸没有）。
   2026 强调"一页讲清再展开"，交付物层面也该有一页。

## 三、反而领先的两点

1. **可执行校验，不只是模板**：2026 那些 GDD 模板（含 OpenAgenticGame-GDD）基本是**文档骨架 + 加权打分**；
   我们有**可复算的断言 / 对账账本 / 主张→证据核对**——是"校验器"，不是"模板"。
   这是从"写得像"跨到"算得对"的一层，模板项目普遍没有。
2. **schema 驱动的条件必填**：底座恒定 + 模块可选 + 品类条件化（combat/economy 这类伪必填会被剔），
   比"一套模板套所有品类"工程化得多；而且**完成度/校验/机读包/导出/评分一条线贯穿**，不会各说各话。

## 四、定位

- 2026 主流：**人读的活模板**（Notion/Confluence/Markdown，靠人自觉）。
- 我们：**机器也认的设计系统**（schema 约束 + 契约 + 校验 + AI 生成），人读的一页视图也有。
- 所以不是"落后于 2026"，而是"**在 2026 的基础上多了一层工程约束**"。缺的是**协作**和**交付物形态（一页纸 / 按读者切）**。

## 五、下一步（按性价比）

1. **一页式导出**（把现有「一页总览」做成可导出的 PDF/Markdown 一页）——成本低、直接补"交付物"缺口；
2. **读者维度**（给字段加"主要读者：程序/美术/测试/数值"标签，导出时按角色切视图）——对应国内系统策划案的做法；
3. **协作**（多人/云同步）——量级最大，最后做。
