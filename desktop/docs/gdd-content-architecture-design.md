## 1. 问题与目标

策划书内容架构要同时满足两件事：

1. **两档产品定位**：标准版 = 核心设计、小白能快速上手、AI 能写；专业版 = 最完整。
2. **补上行业 GDD 骨架里我们缺失的项**：设计支柱、关卡与世界设计、UI·UX 与控制、取舍清单、版本记录
   （外加悬而未决的「与数据有关的开发」该不该单独成章）。

同时不能破坏两天前刚做完的**展示层扁平化**（语义块模型：UI 去「第N章」前缀、无「区」标题），
也不能破坏已锁死的结构不变量。

## 2. 现状（实测，非印象）

### 2.1 当前结构

```
CHAPTER_KEYS = [meta] + NUMBERED_CHAPTER_KEYS         // 17 项
NUMBERED_CHAPTER_KEYS = CHAPTER_PARTS.flatMap(p => p.chapters)   // 16 章
```

| 区 | 章（章号） |
|---|---|
| 一、产品定义 | vision(1) story(2) gameplay(3) |
| 二、游戏系统 | systems(4) combat(5) economy(6) numeric(7) |
| 三、表现设计 | art(8) audio(9) |
| 四、技术方案 | tech(10) |
| 五、制作与发行 | resources(11) mvp(12) risk_handling(13) market_analysis(14) monetization(15) accessibility(16) |

- **标准版** = `[meta, ...LITE_CHAPTER_KEYS]` = 文档信息 + 前 9 章（vision…audio），共 10 项
- **专业版** = `CHAPTER_KEYS` = 17 项

### 2.2 硬约束（决定方案可行性的全部边界）

| # | 约束 | 代码位置 / 守卫 |
|---|---|---|
| **C1** | `LITE_CHAPTER_KEYS` 必须是 `NUMBERED_CHAPTER_KEYS` 的**前缀** ⇒ lite 章号恒 1..9 连续 | `ceshuConstants.ts:161` 注释；`ceshuConstants.test.ts:103-110` |
| **C2** | `CHAPTER_NAMES` / `CHAPTER_REQUIRED_FIELDS` 的 key 集合必须**等于** `CHAPTER_KEYS` | `ceshuConstants.test.ts:59-64` |
| **C3** | `CHAPTER_PARTS` 必须**恰好划分** `NUMBERED_CHAPTER_KEYS`（无重叠、无遗漏、区内不重复） | `ceshuConstants.test.ts:42-57` |
| **C4** | 章号/标签由**数组位置派生**，不手写 | `buildChapterLabels()` / `chapterNumber()` |
| **C5** | lite 长度断言为 **9** ⇒ 改标准版组成是**产品决策**，不是纯技术改动 | `ceshuConstants.test.ts:114` |
| **C6** | 展示层刚扁平化 ⇒ 不得把「区 / 段」重新渲染成标题（会回退刚消除的教科书感） | 已完成的展示层扁平化 |
| **C7** | AI 全量生成调用数 = `visibleChapterKeys(scope).length` ⇒ **每加一章，专业版多一次 LLM 调用** | `ceshuAi.buildFullGeneratePlan` |
| **C8** | 硬编码「第N章·<章名>」会被扫描守卫抓（含自证用例） | `ceshuChapterLabelDrift.test.ts` |

### 2.3 加一章真实要动的地方（关键：迁移本身是免费的）

**好消息**：`normalizeCeshu` 用 `...createDefaultChapters()` 打底、再按 `CHAPTER_KEYS` 覆盖
（`ceshuModel.ts:85-94`）⇒ **新增章会自动以默认值补齐，不需要写新的 migrate 函数**。
旧文件 `version` 仍是 `5.0`，打开即正常。

**真正的成本**在这几处（按"容易漏"排序）：

| # | 位置 | 漏改的后果 |
|---|---|---|
| 1 | `ceshuConstants.ts`：`CHAPTER_KEYS` / `CHAPTER_PARTS` / `CHAPTER_NAMES` / `CHAPTER_REQUIRED_FIELDS` | 直接红（C2/C3 守卫） |
| 2 | `domain/ceshu/ceshuFields.ts:29`：`CESHU_CHAPTER_FIELDS` | 不红，但**新章表单空白、无字段可填** |
| 3 | `domain/ceshu/ceshuDefaults.ts:41`：`createDefaultChapters()` | 不红，但**新章无默认值**，旧文件补不出结构 |
| 4 | `ceshuWordStats.ts`：`WORD_STATS_BENCHMARK` | **静默回落 `FALLBACK_BENCHMARK`** ⇒ 新章字数建议不合理 |
| 5 | `ceshuScorer.ts`：`CHAPTER_WORD_BENCHMARK` | 同上，完成度评分失真 |
| 6 | `ceshuAi.ts`：章节提示词路由 + `buildFullGeneratePlan` | 新章不进 AI 生成计划（或计划项对不上） |
| 7 | `domain/ceshu/ceshuTemplateData.ts`：内置模板 | **套模板后新章空白 = 内容丢失**（历史坑） |
| 8 | `main/ceshu/export/*`：markdown/docx/pptx/html/excel | 导出缺章、TOC 断言红 |

> ⚠️ 第 4/5/7 项是"不红但错"的静默缺陷，typecheck / eslint / vitest 全绿也抓不到 ——
> 与之前「硬编码章号漂移」是同一类，只能靠**显式清单逐项核对**。

## 3. 候选方案

### 方案 A：尾部追加（最小改动）

新增章**全部追加到末尾**（第 17 章起），现有 16 章章号一律不动；新增一个「六、扩展与治理」区容纳。

```
… tech(10) resources(11) mvp(12) risk(13) market(14) monetization(15) accessibility(16)
→ ux(17) level_design(18) data(19) scope(20) changelog(21)
```

- **适用场景**：上线时间极紧（当天）；只想要"行业清单有、我们也有"的条目，不在乎阅读动线。
- **组件划分**：`CHAPTER_PARTS` 加 1 个区；其余按 §2.3 清单同步。
- **数据与调用关系**：不变（`visibleChapterKeys` → 侧栏/AI 计划/导出）。
- **优点**：改动面最小；**零章号重排** ⇒ 现有 e2e / 导出 / 模板断言一行不改；C1 前缀天然满足。
- **缺点**：**语义错位最严重** —— UI·UX、关卡设计（纯设计内容）被排在商业化、本地化之后，
  重现当初"市场分析夹在中间"那类缺陷；专业版读起来像"核心 9 章 + 一堆附录"。
- **风险**：① 与刚建立的"语义相邻"原则冲突；② 未来再加章会持续恶性追加；
  ③ 若新章做成孤立区，与刚做的扁平化观感打架。
- **演进**：只能靠"以后再重排"偿还，届时成本更高（章号 + 断言 + 模板一起动）。

---

### 方案 B：字段化承载（零结构风险）

**不新增任何章节**，把 5 项缺失内容下沉为已有章的字段 / 字段组。

| 缺失项 | 落到哪里 |
|---|---|
| 设计支柱 | `vision` 引导字段（两档通用） |
| 版本记录 | `meta` 字段（文档元信息，本来就不是设计内容） |
| 取舍清单 | `mvp` 字段（"不做什么"属范围管理） |
| UI·UX 与控制 | `art` 字段组（HUD / 菜单 / 操作映射 / 输入反馈） |
| 关卡与世界设计 | `gameplay` 字段组（关卡列表 / 节奏曲线 / 世界结构 / 引导） |
| 数据设计 | `tech` 字段组（待定） |

- **适用场景**：想先低成本补齐"行业清单缺口"，验证这些内容是否真被用到，再决定要不要升格为章。
- **组件划分**：只动 `ceshuFields.ts` + `ceshuDefaults.ts`（+ 可选 `CHAPTER_REQUIRED_FIELDS`）。
- **数据与调用关系**：`CHAPTER_KEYS` / 章号 / 分区 / 前缀**全部不变** ⇒ 100+ 处断言零改动。
- **优点**：零结构风险；lite 前缀不动；**AI 调用数不变（仍 17 次）**；老文档打开后只是多几个空字段，
  **不稀释完成度分母**；改动局限、可分批上线。
- **缺点**：① **专业版"更完整"的感知弱** —— 章节数没变，用户/AI 看不出专业版多了什么；
  ② 与"专业版 = 最完整"的产品定位有张力（真实工作室里关卡设计、UI·UX 确实是独立文档）；
  ③ `gameplay` / `art` 单章变长，**违反"AI 易写"**（上下文被无关字段稀释；本地档还有"提示词 ≤30 行"硬闸）。
- **风险**：① 字段膨胀 ⇒ 单章表单过长、AI 生成质量下降；② 将来若要"按章导出 / 按章评审"，
  字段化内容无法独立成节，需要二次拆分。

---

### 方案 C（推荐）：分层承载 + 专业版段归位

**按「体量 / 独立性 / 是否需要按章评审导出」分层**：薄的做成字段，厚的独立成章，
且**新章插在专业版段首位**（紧接标准版段末尾），让阅读动线回到"设计 → 技术 → 生产 → 商业"。

**第 1 层 · 字段化（两档通用，不动结构）**

| 缺失项 | 落到哪里 | 理由 |
|---|---|---|
| 设计支柱 | `vision` 引导字段 | 3-5 条口号式陈述，不配独立成章；标准版也要有 |
| 版本记录 | `meta` 字段 | 文档元信息；项目已有 `version_label` + 版本 diff 能力 |
| 取舍清单 | `mvp` 字段 | "决定不做什么"是范围管理，独立成章太薄 |

**第 2 层 · 独立成章（full-only，插在专业版段首位）**

| 新章 | 位置 | 理由 |
|---|---|---|
| `ux`（UI·UX 与控制） | **第 10 章**（紧接 audio 第 9 章） | 体量大且是"表现/交互"的延续 ⇒ 与表现设计相邻 |
| `level_design`（关卡与世界设计） | **第 11 章** | 内容设计，排在技术实现之前 |

**第 3 层 · 待定**

| 项 | 状态 |
|---|---|
| `data`（数据设计） | **等"与数据有关的开发"范围明确后再定**：若只是"数据引用与统计"→ `tech` 字段组；若有独立的数据表/数值体系设计 → 独立章 |

**落地后的结构**

```
区：一、产品定义(1-3)  二、游戏系统(4-7)  三、表现设计(8-10)  四、内容与关卡(11)
    五、技术方案(12)  六、制作与发行(13-18)

标准版段：vision(1) story(2) gameplay(3) systems(4) combat(5) economy(6) numeric(7) art(8) audio(9)
专业版段：ux(10) level_design(11) tech(12) resources(13) mvp(14) risk_handling(15)
          market_analysis(16) monetization(17) accessibility(18)
```

- **适用场景**：确认"专业版 = 最完整"是产品主轴，且愿意承担一次性改造（约 2 天）。
- **组件划分**：5 区 → 6 区；`ux` 归入「表现设计」区（跨档位边界是正常的：区只管分组，档位由前缀决定）；
  新增「内容与关卡」区承载 `level_design`（因 C3 要求区必须连续划分，`level_design` 夹在
  表现设计(8-10) 与技术方案(12) 之间，只能独立成区）。
- **数据与调用关系**：不变，仍是 `CHAPTER_PARTS → NUMBERED → CHAPTER_KEYS → 派生标签/章号`
  → 侧栏 / 表单 / 校验 / 进度 / 字数 / AI 计划 / 导出。
- **优点**：① **两段式心智模型**（标准版=核心设计 / 专业版=深度与生产）与产品定位完全对齐；
  ② 专业版段内部按语义归位，消除"关卡设计紧挨版本记录"；
  ③ 只加 **2 章**（不是 5）⇒ AI 调用 17→19（+12%，非 +29%）；
  ④ 3 个薄项字段化 ⇒ 不稀释完成度、不增加调用；
  ⑤ C1 前缀不变（新章在 10、11，天然 ≥10）；与扁平化兼容（段只是**顺序与档位语义**，不渲染成标题）。
- **缺点**：① **tech 及之后的章号 10→12、11→13…16→18 全部重排** ⇒ 导出 / e2e / 字数基准的
  章号断言要同步改（一处不漏）；② 标准版用户看不到任何新章（设计支柱字段除外），
  "专业版更完整"的感知只在切换档位 / 导出时才可见。
- **风险**：见 §5。
- **演进**：M1 字段化（零风险先落）→ M2 加 2 章 → M3 定 `data` → M4（可选）导出层用
  「标准版段 / 专业版段」做分节。

## 4. 推荐与取舍依据

### 推荐 **方案 C**，分两个里程碑落地

**为什么不是 A（尾部追加）**
A 唯一的优点是"零重排"，但它把纯设计内容（UI·UX、关卡）排到商业化之后 —— 这恰恰是当初
分区制重组要消灭的缺陷。而且这个债越晚还越贵（以后章号 + 断言 + 模板一起动）。
既然 C1 已经强制"专业版章只能排在 ≥10"，那**排在哪里**就该按语义选，而不是按"省事"选。

**为什么不是 B（全字段化）**
B 最安全，但它跟"专业版 = 最完整"这个已定的产品定位矛盾：章节数不变、AI 调用数不变，
用户和 AI 都感知不到专业版多了什么。而且把"关卡与世界设计"塞进 `gameplay`、
把"UI·UX"塞进 `art`，会让单章表单明显变长，直接伤害刚确立的目标 —— **AI 易写**
（本地档提示词还有 ≤30 行硬闸）。

**为什么 C 的"章号重排"代价可接受**
`tech(10→12)` 及之后 7 个章号变化，看起来吓人，但它是**机器可枚举**的：
`ceshuChapterLabelDrift` 守卫会立刻抓出任何漏改的硬编码章号，
导出 / e2e 的断言是显式列表，改一次即可。真正危险的是 §2.3 第 4/5/7 项
（字数基准 / 评分基准 / 模板数据）那种"不红但错"的静默缺陷 —— 而这三项**无论选哪个方案都要做**。

**核心取舍**：用「一次性的、机器可校验的章号重排」换「长久的、人每天都要读的语义动线」，
并把"薄项"留在字段层以免无谓地稀释完成度和增加 AI 成本。

## 5. 落地时重点验证的关键点

### 5.1 结构不变量（应立即红）

1. `LITE_CHAPTER_KEYS` 仍是 `NUMBERED_CHAPTER_KEYS` **前缀**，lite 章号 1..9 连续。
2. `CHAPTER_NAMES` / `CHAPTER_REQUIRED_FIELDS` key 集合 == `CHAPTER_KEYS`。
3. `CHAPTER_PARTS` 恰好划分新章节集（无重叠、无遗漏、区内不重复）。
4. `CHAPTER_LABELS` 与 `chapterNumber` 派生一致（C4）。

### 5.2 静默缺陷（不红但错，必须逐项人工核对）

5. **新章默认值**：`createDefaultChapters()` 覆盖 `ux` / `level_design` ⇒ 用真实老 `.json` 打开，
   确认新章以默认值补齐、`version` 不回退、无字段丢失。
6. **字数基准**：`ceshuWordStats.WORD_STATS_BENCHMARK` 必须显式补 `ux` / `level_design`，
   否则静默回落 `FALLBACK_BENCHMARK` ⇒ 新章字数建议不合理。
7. **评分基准**：`ceshuScorer.CHAPTER_WORD_BENCHMARK` 同上 ⇒ 完成度评分失真。
8. **模板数据**：`ceshuTemplateData.ts` 内置模板补新章字段，否则**套模板后新章空白 = 内容丢失**。
9. **AI 路由**：`ceshuAi` 章节提示词覆盖新章；`buildFullGeneratePlan` 按 `visibleChapterKeys(scope)`，
   确认标准版仍是 9 章不变、专业版 17→19。

### 5.3 完成度与成本（容易被误读）

10. **完成度稀释**：专业版分母 17→19，老文档打开后完成度百分比会**下降** ⇒ 确认
    UI / 质量报告文案不会让人误以为"变差了"（可选：新章有内容前不计入分母）。
11. **AI 成本**：专业版全量生成 17→19 次调用；确认 M5 成本护栏（预算条 + 超限二次确认）仍生效。

### 5.4 断言与举证同步

12. **章号漂移**：跑 `ceshuChapterLabelDrift.test.ts`（含自证用例）；导出 markdown/docx 的
    TOC 断言按新章号更新。
13. **e2e**：侧栏点击/断言在扁平化后已按**块名**（无章号）匹配 ⇒ 只需确认新块名不冲突、
    且导出 TOC 的章节数断言同步。
14. **渲染举证**：`preview/shot-parts.mjs` 的期望列表 17 → 19 项，确认新块顺序；
    需 GUI/Playwright 环境实跑（沙箱跑不了）。
15. **模板/示例**：内置模板与示例数据覆盖新章。
16. **回归**：`tsc` 双配置 0 错 / `eslint` 0 / `vitest` 全量绿 / `electron-vite build` 成功。

## 6. 会翻转推荐的前提（待确认）

本次需求描述里**没给**约束，以下是我做的假设；任一不成立，推荐可能改变：

| # | 我的假设 | 若不成立 |
|---|---|---|
| 1 | **允许重排专业版段章号**（tech 及之后 10→12…） | 若要求"现有章号一个都不能动" ⇒ **退回方案 A** |
| 2 | **标准版固定 9 章**（C5） | 若要把某个新章（如 `level_design`）纳入标准版 ⇒ 需先改 `toHaveLength(9)`，属产品决策，方案整体重排 |
| 3 | 优化目标是 **AI 易写 + 人易读**（刚扁平化的目标） | 若目标变成"章节数最少/改动最小" ⇒ **退回方案 B** |
| 4 | 一人 + AI，改造**分 M1/M2 两步** | 若有硬性 deadline（如 1 天）⇒ 只做 M1（字段化），M2 延后 |
