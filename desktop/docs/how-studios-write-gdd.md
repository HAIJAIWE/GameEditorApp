# 商业大厂到底怎么写 GDD？（能查证的部分 + 不能查证的部分）

> 用户问：Rockstar / 米哈游 / 腾讯那种内部 GDD，是「模板」还是什么？
> 诚实前提：**这些公司的内部设计文档不公开。** 网上能看到的，没有一份是官方发布的大厂内部 GDD。
> 下面按「证据可信度」分层说，不把传说当事实。

## 一、能查到的三类「证据」（可信度从高到低）

| 层级 | 是什么 | 例子 | 能信多少 |
|---|---|---|---|
| ① 公开设计圣经 | 老派、已公开的真实设计文档 | Doom Bible(1992)、Grim Fandango 谜题文档 | 真，但**老/单一品类**，不代表现代大厂 |
| ② 泄露的内部模板 | 带「公司内部文档严禁外传」字样的模板/规范 | 流传的 RPG 策划案模板 | **结构可参考，内容不可复制**；且多为旧版 |
| ③ 行业培训/博客方法论 | 策划教学、CSDN/百家号/文库 | 「系统设计文档怎么写」类文章 | 反映**普遍做法**，但非某公司官方 |

**结论：Rockstar / 米哈游 / 腾讯的真实内部文档，外部没有。** 网上所谓「腾讯策划模板」，多半是培训材料或文库上传，**真假参半，别当铁证**。

## 二、中文行业里「普遍这么做」（来自可查的行业指南，非某厂官方）

1. **不是一份大 GDD，而是「按系统/功能拆分的执行文档」。** 战斗、背包、任务、商城、社交各自成文，固定格式：
   `系统目标 → 功能入口 → 界面布局 → 功能流程 → 规则说明 → 异常处理`（异常处理最容易被漏，也最省返工）。
2. **「设计案」和「执行案」分两步。** 先在 XMind 脑图出备选方案 → 和主策定方案 → 再写正式文档（执行案）。
3. **数值用 Excel 表，文档只写思路。** 改表不改文档，避免「文档和数值两张皮」。
4. **在线文档协作迭代**（腾讯文档 / 飞书 / Confluence），不是 Word 定稿——文档是**活的**。
5. **文档是沟通工具，不是文笔展示。** 针对不同读者写不同重点：程序要逻辑与配置、美术要资源清单、数值要投放与曲线、测试要功能细则、制作人要影响与排期。
6. **大厂确有内部规范/模板**（甚至有「严禁外传」标记），但那是**脚手架**，真正的产出是上面的执行文档。

## 三、对我们这套（24 章 schema）的启示

| 现实做法 | 我们的现状 | 判断 |
|---|---|---|
| 按系统/功能拆分的执行文档 | 我们按「章」组织，粒度更粗 | ◐ 方向对，但**「章」不如「系统/功能」细** |
| 数值用 Excel / 结构化表 | 我们 pipeList + 机读断言/账本 | ● 同精神（结构化 > 散文） |
| 在线文档活迭代 | 我们有版本/迁移，但单机 | ◐ 活文档方向对，缺协作 |
| 文档=沟通工具，按读者写重点 | 我们 `reviewHint` 是**自检**视角 | ⚠ 缺「**写给谁看**」这一维（程序/美术/数值/测试） |
| 设计案 → 执行案两步 | 我们 AI 起草 → 人审定稿 | ● 可对应，但没显式分「方案 vs 执行」 |

**最有价值的两个新点**：
1. **读者导向**：真实文档强调「这段是给程序看的还是给美术看的」。我们的 `reviewHint` 目前只帮审阅者自检，可补一个「受众」维度。
2. **设计案/执行案分离**：对应我们「AI 起草（方案）→ 人审定稿（执行）」，可以在 UI 上显式标注「草稿/定稿」两种状态（我们已有 `status` 字段，但没和起草流程绑）。

## 四、一句话

大厂内部不是「一份 GDD 模板」，而是**「内部规范 + 按系统拆的执行文档 + Excel 数值 + 在线协作」的组合**。
模板只是脚手架，真正决定质量的是「写给谁看、逻辑是否可执行」。**具体某公司怎么写，外部看不到，别信传言。**
