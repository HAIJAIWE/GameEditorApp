fix(agent): Function Calling tools 线格式（云端 400 / 本地静默失效）+ Qwen 档默认模型

主理人在数字员工面板云端档实测命中 HTTP 400
`InvalidParameter: input.tools.0.type must be one of ['function']`。

根因：toJsonSchema() / SkillDispatcher.toolsJsonSchema() 产出的是**内层**
{name,description,parameters}，brainService 把它原样塞进 BrainLlmRequest.tools，
两个传输层又原样下发；而 OpenAI 兼容端点与 Ollama /api/chat 都要求每个元素是
{type:'function', function:{…}}。

⚠️ 本地档同样是错的，只是「不报错」：Ollama 忽略未知字段、function 解析成零值
⇒ 模型拿到一个没有名字的工具，表现成「模型完全不会用工具」——很可能就是长期
被归因为「4B 不行 / 提示词冗长税」的真因之一。

修法（一处转换、两处透传）：
- protocol.ts 新增 ToolFunctionSchema + toFunctionCallingTools()
- brainService.chat() 成为全项目唯一转换点
- openAiTransport / ollamaTransport 保持透传并写死契约；空 tools 时省略该键
- dispatcher.toolsJsonSchema() 改用具名类型（保持内层形态，agent:listTools 的 UI 在用）

为什么之前没被测出：既有断言只打 tools[].name、从不看 .type —— 断言打偏了层。
⇒ 新增守卫：协议（包装 + 反摊平）/ 装配（云端·本地·显式选择三路线格式）/
传输层（透传 + 空 tools 省略）/ e2e 桩（function.name + type==='function'）。

同期校正 Qwen 档默认模型（主理人截图所在档位）：models[0] 由整份清单最弱的
qwen-turbo 抬到 qwen3-max，剔除旧预览 id qvq-max-2025-03-25（依据百炼官方
Function Calling 支持列表）；deepseek-v4-pro / deepseek-v4-flash 同批得到旁证。

验证：vitest 129 文件 / 2001 用例 passed；tsc 0（node+web）；eslint 0；
CSS 审计仅 5 处已知模板噪声；build 通过（CSS 110.48 kB 不变）。
